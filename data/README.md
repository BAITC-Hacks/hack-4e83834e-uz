# Data — sources, schema, and synthetic generation logic

RoadWatch combines three kinds of data. This document states plainly which
parts are real and which are synthetic, per the project's data-honesty
requirement — nothing here is presented as real open government data unless
it explicitly says so (nothing currently is: see below).

## 1. Detection training images — real, individually sourced

13 real photographs of road potholes/cracks, downloaded individually from
Wikimedia Commons (not a bulk dataset — see `/model/README.md` for why).
Full attribution, license, and source URL for every image is in
`backend/data/sample_images/SOURCES.md`. Hand-drawn bounding box
coordinates are in `backend/data/detect_dataset/ANNOTATIONS.md`.

We looked for an accessible open road-damage dataset (RDD2022, Kaggle
pothole sets) first; both require credentials/an account this environment
didn't have, so we fell back to this small, real, individually-licensed
set rather than fabricate images. This is exactly the fallback the project
brief anticipates ("falling back to a documented synthetic approach if
not [accessible]") — see `/model/README.md` for the honest accuracy
consequences of that choice.

## 2. Traffic volume — 100% synthetic (documented)

No open per-road-segment traffic count data (real city traffic sensors,
open-data portals) was reachable from this environment. `daily_traffic` on
every `RoadSegment` is generated by `backend/app/scoring/traffic_sim.py`:

- Each segment has a `road_class` (`arterial` / `collector` / `local`),
  which sets the center of a **lognormal distribution** of daily vehicle
  counts (`arterial≈12000`, `collector≈4000`, `local≈900`, σ=0.35 in log-space)
  — this mirrors the real-world fact that arterial roads carry much more
  traffic than local streets, without claiming to model any specific city's
  actual counts.
- A **per-district multiplier** (1.4 down to 0.75) nudges central/business
  districts busier than outer residential ones — a coarse proxy for the
  real correlation between traffic and land use.
- Generation is seeded per-segment (`seed = segment_index * 97 + 7`) so the
  same segment always gets the same synthetic traffic value across runs.

**This is not real Almaty traffic data.** It exists purely so the priority
score has a traffic feature to combine with severity and repeat-reports.
See `traffic_sim.py`'s module docstring for the exact formula.

## 3. Road segments & districts — illustrative geography

`backend/app/seed.py` creates 24 road segments (4 per district) across six
Almaty district names (Medeu, Bostandyk, Almaly, Auezov, Nauryzbay,
Turksib) with **approximate, illustrative district-center coordinates**
(hand-picked, not sourced from an authoritative GIS boundary file), jittered
randomly (±0.02°) per segment, and given plausible-sounding street names
drawn from a fixed list of real Almaty avenue names (Abay Ave, Al-Farabi
Ave, etc. — these are real street names, but the specific segment↔street
pairing is arbitrary/synthetic).

**Why Almaty**: purely for a realistic-feeling demo (the hackathon judge
audience is presumably local/regional) — the pipeline itself is not
Almaty-specific and the district list is a config constant
(`app/seed.py:DISTRICT_CENTERS`) that could be swapped for any city.

## 4. Defect & report volume — mixed real + synthetic

- **9 defects** come from running the real fine-tuned YOLOv8 detector
  against the 13 real sample images (`model_source: "roadwatch-finetuned"`).
- **40 defects** are purely synthetic (`model_source: "seed-synthetic"`):
  random defect class, confidence (uniform 0.35–0.95), and area% (uniform
  within a class-appropriate range) — generated only to give the demo
  dashboard enough volume to look like a real queue/map/analytics view. No
  detector was run on these; their "photo" is a randomly-reused stand-in
  image, not evidence of an actual defect at that location.
- **Repeat reports**: ~30% of defects get 1-4 extra synthetic `Report` rows
  with `submitted_at` timestamps spread over the past 0-18 days, to
  demonstrate the time-decayed repeat-report clustering
  (`scoring/repeat_reports.py`) in the demo.
- **A few pre-reviewed defects**: 8 random defects are seeded with an
  `ApprovalLog` entry (random reviewer name from a fixed demo list, random
  approve/reject/defer action) purely so the dashboard's analytics/history
  views have something to show immediately, without requiring you to
  manually review anything first.

Run `python -m app.seed` to (re)generate this - it's idempotent (drops and
recreates all tables each time).

## 5. Schema

| Table | Key columns | Notes |
|---|---|---|
| `road_segments` | `district`, `road_class`, `lat`, `lng`, `daily_traffic` | `daily_traffic` synthetic (see §2) |
| `defects` | `defect_class`, `confidence`, `x1..y2`, `area_pct`, `model_source`, `status` | `status` only changes via `POST /defects/{id}/review` |
| `reports` | `defect_id`, `segment_id`, `source`, `submitted_at` | one row per citizen/dashcam/inspection submission; repeat reports on the same defect drive the repeat-report score |
| `approval_logs` | `defect_id`, `action`, `reviewer_name`, `decided_at` | immutable log, one row per human decision |

`model_source` is deliberately kept on every `Defect` row
(`roadwatch-finetuned` / `pretrained-coco` / `seed-synthetic`) so the API
and dashboard can always show whether a given item came from real
detection or demo seed data - this is the mechanism that keeps the
"don't hide synthetic data" constraint enforced at the data level, not
just in prose.

## 6. Known limitations

- No real traffic, repeat-report, or district-boundary data was used
  anywhere in this prototype - see §§2-3.
- Seed volume (40/49 defects) intentionally dwarfs real-detection volume
  (9/49) to make the demo dashboard look populated; don't read total counts
  in the Analytics page as evidence of real defect prevalence.
- District/segment geography is illustrative, not survey-grade.
